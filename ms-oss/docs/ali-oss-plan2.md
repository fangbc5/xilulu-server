# 进阶企业级 OSS 架构设计方案 (Advanced Enterprise Architecture)

如果您希望超越“简单可用”，追求**真正的高并发、高吞吐、职责单一的微服务企业级架构**（类似阿里、字节跳动的内部设计），我们需要彻底将“重型计算（图片/视频转码）”从 `ms-oss` 业务核心服务中剥离出来。

之前的方案（JIT 进程内处理）在面临大流量或超大视频时，会导致 `ms-oss` CPU/内存飙升，发生 OOM 或阻塞其他上传/下载请求。真正的企业级方案应当采用**职责解耦**和**异步事件驱动**设计。

---

## 核心设计思想

1. **计算与业务解耦**：将所有媒体处理（图片裁剪、视频抽帧）移出 `ms-oss`。
2. **术业有专攻**：图片采用业界标准的边缘处理网关（如 `imgproxy`），视频采用异步事件流（Kafka + Worker）预处理。
3. **网关层签名下放**：下载流量甚至不应该经过 `ms-oss` 的应用容器，而应该由 API Gateway（网关层）或 Nginx 校验签名后直连 MinIO。

---

## 模块化增强方案

### 1. 动态图片处理：引入专用的图片处理引擎 (推荐：imgproxy)
**场景**：实时、高频地进行图片裁剪、缩放、格式转换（如实时转 WebP）。
**企业级痛点**：图片处理极其消耗 CPU，且容易受到“图片炸弹（Image Bomb）”攻击导致 OOM。
* **架构方案**：
  * 在 `docker-compose` 中新增部署业界标准的顶级开源图片处理服务 `imgproxy`（由字节、Discord 等大量使用）。
  * **流程**：
    1. 用户访问 `ms-oss` 的短链接 `GET /api/v1/oss/img/*key?x-oss-process=image/resize,w_200`
    2. `ms-oss` 进行鉴权后，**不自己处理图片**，而是通过加密签名机制，生成一条合法的 `imgproxy` 内部 URL。
    3. `ms-oss` 返回 HTTP 302，将用户重定向到网关层的 `imgproxy` 路由。
    4. `imgproxy` 从底层的 MinIO 拉取原图，利用底层的 C/C++ 库（libvips）极速处理，返回给用户并在 CDN 或其自身附带存有缓存。

### 2. 视频抽取缩略图：事件驱动的异步媒体管道 (Event-Driven Pipeline)
**场景**：大视频（几十MB到几个GB）的截帧、转码。
**企业级痛点**：视频处理是重 IO 和重 CPU 的操作，如果使用 JIT（用户请求时实时去抽帧），HTTP 请求极大可能超时，体验极差。
* **架构方案**：
  * 采用 **CQRS / 异步事件流** 架构，利用 `fbc-starter` 中的 Kafka 支持。
  * **流程**：
    1. **触发**：客户端完成视频上传并调用 `POST /oss/callback`（上传成功回调）时，`ms-oss` 将该文件的信息（`file_id`, `path`）作为事件发送到 Kafka 的 `oss-media-processing-topic`。
    2. **处理**：引入一个新的微服务角色（或者让专门的 Worker 节点去执行），消费该 Topic。
    3. **执行**：Worker 节点异步拉取视频，使用内部的 `ffmpeg` 抽取首帧（甚至进行多码率转码 M3U8）。
    4. **回写**：处理完成后，Worker 将截图上传到 MinIO，并调用 `ms-oss` 的内部 API，将截图的 URL 更新到主数据库的记录中。
    5. **展示**：用户在聊天列表/会话里，获取到的直接就是已经预处理好的缩略图物理 URL。无需附加 `?x-oss-process`。

### 3. 长效下载签名机制：网关层直连 (Gateway Direct Access)
**场景**：需要为用户发放长期的防盗链下载地址，同时减轻核心服务的负担。
**企业级痛点**：不管采用哪个方案，如果通过 `ms-oss` 代理流量或频繁做 302 重定向，在高并发时依然有性能损耗。
* **架构方案**：
  * 改用 **网关层（ms-gateway/Nginx） HMAC 校验**。
  * **流程**：
    1. `ms-oss` 暴露生成链接接口：通过应用的 Secret Key，利用统一算法生成带有有效期（如 1 年）和资源路径的 URL，如 `https://domain/files/*key?expire=17100000&sign=ab123...`。
    2. **不经过 `ms-oss`**：下载时，域名直接指向外部网关（如带有 Lua 脚本的 Nginx / APISIX / 或对 Rust `ms-gateway` 进行改造）。
    3. 网关层基于同样的 Secret Key，校验 `sign` 是否匹配且未过期。
    4. 如果校验通过，网关直接充当反向代理（Reverse Proxy），将请求路由给内网的 MinIO 节点获取流并返回，全程免去 `ms-oss` 的参与。

## 方案对比总结

| 特性 | 当前方案 (Plan 1 - JIT 重定向) | 进阶方案 (Plan 2 - 专用服务+事件驱动) |
| :--- | :--- | :--- |
| **开发成本** | 低（单机 Rust 直接调用库即可） | 较高（需引入 imgproxy，配置 Kafka 流转，修改网关） |
| **处理性能** | 一般（受限于 Rust 单机性能和 I/O 阻塞） | **极高**（libvips C++ 处理图片，异步预计算视频） |
| **稳定性** | 容易遇到视频大文件处理导致的 OOM/Timeout | **完全隔离**（长耗时任务在 Worker 执行，不影响主干服务） |
| **网络出口压力** | 低（302 跳转让客户端直连） | **极低**（网关层直连和流转） |
| **业界适用度** | 中小厂规模 | 大中型厂、视频/图片富媒体平台 |
