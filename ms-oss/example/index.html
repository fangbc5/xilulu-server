架构特征

Zero-Copy 理念
核心文件上传流绝不经由业务网关或 ms-oss 后端转发。所有大文件统一通过服务端签发的 Pre-signed S3 URL 由前端直传到对象存储层（Rustfs/MinIO），极大释放了微服务的带宽。
边缘计算 (Edge Computing)
图片裁剪等高发请求被前置到了 Nginx OpenResty 层，通过直接翻译 x-oss-process 指令配合 imgproxy，将毫秒级耗时降至极限，彻底消除了后端的重定向请求剥夺。

POST /oss/signature

预签名安全直传

为保障服务端带宽不受大型文件上传影响，我们采用预签名(Presigned URL)直传机制。客户端需向后端声明意图，拿到临时通行证后直接连接对象存储服务器。

Step 1: 申请临时凭证

提交文件元数据和业务场景（如 avatar 仅允许上传不超过 5MB 的图片），向服务器换取直传的 PUT URL 和 Object Key。

const payload = {
  "method": "put",
  "bucket": "public",
  "scene": "avatar",
  "filename": "user_upload.png",
  "content_type": "image/png",
  "size": 102400
};

const response = await fetch('/oss/signature', {
  method: 'POST',
  body: JSON.stringify(payload)
});
const signatureData = await response.json();
// signatureData.data 包含 url (上传用的超长链接) 和 object_key

Step 2: 客户端直传 S3

使用上一步返回的 url，利用 PUT 方法将二进制流本身发送到 S3 节点。注意：ContentType 头必须与申请阶段一致。

const rawFile = document.getElementById('fileInput').files[0];

const uploadResponse = await fetch(signatureData.data.url, {
  method: 'PUT',
  body: rawFile,
  headers: {
    'Content-Type': rawFile.type
  }
});
if (uploadResponse.ok) {
  console.log("Success! Assigned Key:", signatureData.data.object_key);
}
完全解耦的数据落库
前端直传成功后 无需发起回掉通知请求。S3/MinIO 会通过 Kafka 抛出落盘事件，ms-oss 在后台无感抓取并持久化至 file_meta 表。
GET /oss/{bucket}/{key}?x-oss-process=...

图片边缘动态计算

系统兼容阿里云语法规范。我们并未将流量路由到 Rust 后端，而是通过带有 FFI 模块的 OpenResty，实时拦截指令、执行高性能 HMAC-SHA256 签名计算并透传给并行的底层运算集群。

实时性能监控仪

在右侧拖拽滑块，查看下方 CDN Badge 的瞬时转变：

❌ MISS (70-150ms)代表计算节点正首次拉取 S3 原图进行解码渲染。
⚡ HIT (2-10ms) 代表 Nginx CDN 边缘节点已由内存高速分发静态文件。

受支持的边缘指令

// 调整大小与质量
?x-oss-process=image/resize,w_300,h_300/quality,q_85
// 格式无损转换
?x-oss-process=image/format,webp
// 命名预设样式 (Style)

预签名受限下载

由于对象存储(S3)大多配置为私有读写权限以防盗刷，当用户或下游系统需要获取原文件时，应当签发一条具有严格时效的 GET 类型预签名链接。

Step 1: 申请下载凭证

不同于通过 CDN + url 暴露（适用于公开分享的展示类图片），针对私密合同、用户数据包等敏感文件的主动下载操作，后端将请求底层集群发放高复杂度的 URL。

const payload = {
  "method": "get",               // 标记类型为下载/拉取
  "bucket": "public",
  "key": "avatar/user-info.zip",
  "expires_in": 300              // 极其短暂的有效存活时间 5 分钟
};

const response = await fetch('/oss/signature', {
  method: 'POST',
  body: JSON.stringify(payload)
});
const signatureData = await response.json();

Step 2: 客户端消费凭证

得到的临时 url 可以直接分配给 A 标签或者被 302 跳转触发浏览器安全的拉取行为。由于底层 S3 签名的保护，请求伪造将被直接拦截。

const downloadUrl = signatureData.data.url;

// 使用系统下载能力触发
const a = document.createElement('a');
a.href = downloadUrl;
a.target = "_blank";
document.body.appendChild(a);
a.click();
document.body.removeChild(a);
POST /oss/{b}/{k}?uploads

大文件并行分片

面对 1GB 上下的大体积文件或弱网环境，必须采用分片并发直传。我们遵循 S3 体系最标准的三步走握手协议：初始化 (Init) → 独立上传 (Put Parts) → 合并 (Complete)。

Step 1: Init 初始化任务

提交总大小及预期分片大小，获取 UploadID 与一批签发好的 PUT URLs。

const res = await fetch(`/oss/public/big_file.mp4?uploads=1`, {
  method: 'POST',
  headers: {
    'x-oss-meta-scene': 'chat_video',
    'x-oss-meta-total-size': file.size,
    'x-oss-meta-part-size': 5242880 // 5MB
  }
});
// 拿到 res.data.upload_id 与 res.data.parts (预签名 URL 数组)

Step 2: 并行 Put 直传

无需跟后端通讯！利用上一步的分配额度，多线程并发 PUT，极其关键的是：记录底层 S3 返回的 ETag。

const etag = s3Response.headers.get("Etag");
// 保存 { part_number: 1, etag: etag }，以此类推完成所有分配的分片上传

Step 3: Complete 合并组装

收集全部 ETag 证据，带着 uploadId 报告给后端触发集群合并数据。

await fetch(`/oss/public/big_file.mp4?uploadId=${uploadId}`, {
  method: 'POST',
  body: JSON.stringify({ parts: [ { part_number: 1, etag: "..." }, ... ] })
});
// 合并成功后，Kafka 事件会自动流转处理剩下的事
KAFKA Event-Driven Video Async

流视频长效截帧处理

由于多媒体视频解码属于极具破坏性、重 CPU 的高危操作（FFmpeg），本模块被严格剥离到了专门的微服务环境（ms-media-processor）。

完全的零阻滞长线异步

视频直传完毕瞬间即可呈现界面刷新。底层经过：

Upload ➔ Kafka 事件 ➔ ms-media-processor 嗅探流 ➔ 并行抽出首帧 ➔ 再传对象存储 ➔ 发送回执写表

整个链路中，前端只需要静静地依赖 HEAD 请求短轮询（或者监听长连接 Websocket 通知）来获悉 x-oss-meta-thumbnail-key 字段的显现，便可优雅地呈现预览图并实现高度解偶的设计。

防盗链长效脱敏分享

暴露原始资源路径和配置到公网极不安全（易遭遍历），而且前端往往难以统一对聊天窗口的历史海量照片应用动态调整方案。

JWT 携带工艺

此时向后端请求签发 method: share，我们可以将有效期、特定的处理需求（例如规定此分享链接打开必须是一张打满高斯模糊的马赛克微缩图）直接内聚强加密烧进 URL Token 中，从而下发给不受控的 C 端分发域确保资产绝对无忧。

GET /oss/share/eyJhbGciOiJIUzI1Ni...
// ➜ HTTP 302 Found
// ➜ Location: http://.../rs:fit:100/plain/...
